Summary

On 2026-05-17/18 we built Maple’s Vertex AI orchestration for PDR2 patient-conditional fine-tune and evaluation, ran the first real foundation-model fine-tune for Maureen (Track A: zero PRS + real Caris MI Profile expression on the PrimeKGCIViCPharmGKBMaureen graph), and confirmed via synthetic positive-control test that our pipeline faithfully reproduces the paper’s apply_personalization mechanism. The fine-tune produced interpretable criterion weights (top protein-side weights on ADORA2A, TSC2, SSTR2, NRG1, CCNE1 — biologically reasonable for Maureen’s tumor) but no MRR lift on her held-out edges at λ₂=0.01 (Δ_MRR = −0.41% vs foundation baseline). A synthetic test with extreme parameters (TP53 anchor, w=1.0, expr=100, λ=1.0) produced the predicted dramatic score shifts, confirming the pipeline math is correct. The same synthetic test surfaced an architectural limitation of the paper’s design: the drug-only adjustment mask isolates receivers but not non-drug-tail queries, because rankings are over all 139K entities — boosted drugs pollute the top of every ranking regardless of the query’s true tail type. This is the paper’s design as faithfully reproduced; addressing it for general KG completion (Maureen’s heterogeneous tail-type queries) would require a per-relation criterion architecture, deferred. With OncoKB now license-approved as of this morning, the next concrete move is to land Phase 8.5 (variant-aware KG with OncoKB chains) and retrain the foundation against a richer Maureen overlay — making the fine-tune meaningful at normal λ, not just synthetic extremes.

1. Purpose

PDR2’s personalization mechanism had three open questions when we started:

  1. Does it run end-to-end on Vertex AI? Phase 1 of the PDR2 training automation plan (an internal note on the training-automation status) had reached aiplatform.CustomJob.submit() but was blocked on quota. We confirmed quotas, ran the first real training, and added two new container modes for fine-tune and personalized eval.
  2. Does the mechanism produce signal on Maureen’s data? The 2026-05-09 writeup (docs/pdr_personalization_writeup.md) documented the loss formula and apply_personalization algorithm. This run was the first end-to-end empirical test.
  3. Does our implementation reproduce the paper faithfully? We could not distinguish “real null result” from “wiring bug” without a positive control. A synthetic-data sanity test resolved this.

Out of scope for this run: variant-aware KG (Phase 8.5 — unblocked this morning by OncoKB license approval; deferred to a follow-up session), Track B (requires Maureen’s genotype upload), λ sweep on real data, real-data eval at non-default lambdas.

3.3 Synthetic positive control

To distinguish “real null result” from “wiring bug,” we constructed a synthetic patient + criterion bundle designed to produce a predictable and dramatic score shift if the pipeline is wired correctly:

  • Anchor: TP53 (NCBIGene:7157)
  • protein_weights = tensor([1.0]) (hand-set, not gradient-trained)
  • expr_values = [100.0] (hand-set)
  • disease_weights = tensor([]) / prs_values = [] (no disease channel)
  • λ₂ = 1.0 (100× default)
  • Predicted per-entity adjustment for 1-hop TP53 neighbors: 1.0 × 1.0 × 100.0 = +100.0

Raw foundation scores observed on Maureen’s queries are in the [10⁻⁴, 10⁻²] range; a +100 additive offset must catastrophically dominate. The exact predicted observable: any entity 1-hop-adjacent to TP53 should rank near the top of every Maureen-anchored query, regardless of the query’s actual semantics.

Built via backend/scripts/build_synth_finetune_bundle.py.

3.4 Evaluation methodology

We score Maureen’s outbound edges in valid+test splits (138 edges across 11 predicates) by ranking all 139,226 candidate tails per query. Metrics:

  • Filtered rank: number of entities with score strictly greater than the true tail’s score, excluding other known-true tails for the same (head, relation) pair, +1.
  • MRR: mean(1/rank) across edges; bounded [0, 1]; random baseline = 1/139,226 ≈ 7.2×10⁻⁶.
  • Hits@k: fraction of edges with rank ≤ k; bounded [0, 1].

The eval is over the entire entity vocabulary (139K), not over a candidate set restricted to drugs. This is the same protocol our baseline eval_patient uses; it’s stricter than the paper’s protocol (which scores only drug-tail queries against drug candidates), but it lets us evaluate Maureen’s heterogeneous tail-type predicates honestly.

4.4 Architectural finding: cross-predicate noise

Synth v3 surfaces something the paper’s eval scope hid. Even with the paper-faithful drug-only restriction, gene-tail predicates moved (some by 13–31%). Why?

The ranking is over all 139,226 entities by final_score = raw_score + adj. With +100 boost on ~7,782 TP53-adjacent drugs, every TP53-adjacent drug that previously had raw_score below the true gene-tail now ranks above it. The gene-tail’s rank gets worse by that count.

For predicates where the true tail’s raw rank is already very high (e.g., has_variant, has_phenotypic_feature — raw MRR < 10⁻³, true tail ranks below most things anyway), few TP53-adjacent drugs are below them in the first place, so nothing changes. For predicates where the true tail had a good raw rank (has_genetic_alteration_in, raw MRR 0.025 ≈ rank 40), many TP53-adjacent drugs were below it, and now they’re all above.

This means: the drug-only mask isolates the receivers, but doesn’t isolate non-drug queries from the boosted-drug pollution. The paper avoided this because they only evaluate drug-tail queries against drug candidates. For Maureen’s heterogeneous tail-type ground truth (genes, drugs, variants, phenotypes mixed), the paper’s mechanism has an inherent cross-predicate noise floor.

This is a real architectural limitation of the paper’s design for general KG completion. Phase 12 (specialist per-relation criteria — see paan_planning.md) is the natural extension that would eliminate it.

6. What Now Works

End-to-end Vertex pipeline:

  1. Local builder: build_pdr2_input_pickle.py --source synthetic_zeros produces pickle + resolution sidecar.
  2. Local builder: build_synth_finetune_bundle.py produces synthetic test artifacts (no fine-tune needed).
  3. GCS upload via gcloud storage cp.
  4. Foundation pristine-copy from Drive (manual one-time per source run).
  5. Submit Vertex CustomJob via gcloud beta ai custom-jobs create --config=<json> — supports modes fine_tune, eval_patient, evaluate_personalized.
  6. Outputs land in GCS; manual inspection / download.

Verified to work:

  • Foundation pristine-copy + fine-tune produces interpretable criterion weights (Section 4.1).
  • Baseline eval_patient scores Maureen’s edges against foundation only.
  • evaluate_personalized scores Maureen’s edges against foundation + criterion adjustment.
  • adjustment_target_domain=drug faithfully reproduces the paper’s apply_personalization.
  • adjustment_target_domain=any extends to all entities (broader receivers, but cross-predicate noise).
  • OOM auto-probe finds the largest fitting batch (e.g., 128 on A100-80GB for this graph).
  • NumPy 2.x ↔ 1.x pickle portability (lists, not arrays).

Still requires manual orchestration:

  • Job submission is by hand (not auto via the worker handler).
  • Foundation training itself happens in Colab; we copy artifacts to GCS.

7. Architectural Findings — Things to Remember

7.1 The classify_entity-Biolink gotcha

The upstream TransductiveDataset.classify_entity (lib/pdr2/code/ultra/datasets.py:260) assumes the paper’s naked-identifier convention. Our KG uses Biolink-style CURIEs. Without the patch, every entity falls into gene_inv_vocab, breaking the paper-faithful drug-only restriction in apply_personalization. Any future PDR2 fork using our data will hit this — the symptom is adjustment_target_entity_count: 0 (or whatever count = “no drugs found”). Saved in memory.

7.2 The personalized loss is gradient-degenerate

As coded (losses.py:60-86), the criterion’s gradient depends only on (criterion_weights, fixed_patient_values) — not on batch contents. 20 epochs and 1 epoch converge to the same optimum. The paper’s TEXT suggests a per-triple score multiplier in the loss; the CODE doesn’t have one. We faithfully reproduce the code. Saved in memory.

7.3 Drug-only mask isolates receivers, not queries

Already documented in §4.4. Important enough to call out separately: even with the paper-faithful restriction, Maureen’s gene-tail and variant-tail queries are noisily affected by drug-receiver boosts, because rankings span the whole entity vocabulary. Saved in memory.

7.4 Vertex AI ↔ Maple-data prefix mismatch is a recurring failure mode

Beyond classify_entity, two other code points needed Maple-side patches:

  • eval_patient.py:179-184 and evaluate_personalized_maple.py:328-339 looked for vocab keys inv_entity_vocab / inv_rel_vocab; the dataset actually saves them as entity_dict_forward / relation_dict_forward. Fixed with a fallback chain.
  • apply_personalization itself (training.py:198+) has a hardcoded author-local vocab path (/usr/homes/cxo147/...) that we do not currently invoke directly; our evaluate_personalized_maple.py reimplements the adjustment logic to avoid needing the typed-vocab pickle at that path. If anyone ever wants to call upstream evaluate_model_personalized directly, this path will need to be parameterized.

7.5 NumPy 2.x / 1.x pickle cross-version incompatibility

Local Maple env is NumPy 2.x; the PyTorch 2.1 base image in our container is NumPy 1.x. pickle.dump(np.ndarray, ...) from one side fails to load on the other (ModuleNotFoundError: 'numpy._core'). Fix: serialize as Python lists in the pickle. Saved in memory.

7.6 L4 capacity is unreliable in us-central1 right now

We had quota for L4 granted but the Vertex jobs sat in PENDING for hours waiting for actual hardware availability. A100-40GB and A100-80GB capacity was reliable. For eval jobs (which don’t actually need 80GB), switching to A100-40GB resolved provisioning. Saved in memory.

8.2 What’s not addressed by Phase 8.5

OncoKB doesn’t fix:

  • The gradient-degeneracy of the loss (§7.2) — still need Phase 12 or paper-equivalent loss rework if we want criterion gradient to actually use batch information.

  • The lack of a true validation gold standard for personalization on Maureen — RGCC (pdr_phase7_5_rgcc_writeup.md) is the closest, but it’s drug-tail-only. For variant or expression tails, we’d need clinical follow-up or separate ground-truth construction.
