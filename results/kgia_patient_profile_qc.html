KGIA Patient Profile — Data QC Checklist

Use this document to track data-quality review of every section that feeds the KGIA fine-tuning input file (GET /api/mods/research/patient-profile). One row per section. Check the [ ] once we’ve QC’d that section’s data and confirmed the records, the query shape, and any cleanup are good.

The “final file” = whatever the API returns when you toggle on the sections you want. Toggling a section off in the UI also drops its entities from PrimeKG coverage, so this is the same gate KGIA will see.

  • Schema: kgia-profile/1.1
  • Endpoint: GET /api/mods/research/patient-profile?include=<csv-of-section-keys>
  • Builder: backend/mods_kgia_profile_service.py
  • Frontend: frontend/src/components/ResearchDashboard.jsx → “Patient Profile” tab

Always-on (no toggle)

How sections were chosen for v1

Three filters, in order:

  1. MEMORY notes about Maureen’s record. The “Genomic report parsing COMPLETE (2026-03-18)” memory enumerates the tables MODS parsers populated (alterations, gene expression, therapy associations, resistance factors, CTC profiles, drug sensitivities). Picked exactly those, plus their dependencies.
  2. Existing snapshot service coverage. ModsSnapshotService already builds patient + cancer + biomarkers + treatments + RGCC. Kept those, added the post-snapshot tables.
  3. KGIA’s input shape. --use_ploss consumes a PRS scalar + biomarker scalars + a patient-local KG. Anything that gives us biomarker scalars or KG-mappable entities (genes, drugs, diseases) earns a section.

What can contribute to the final file

Strictly: anything we choose to feed in. The KGIA loss is λ₁·PRS + λ₂·biomarker, so the floor is just PRS + biomarker scalars. Everything else expands the patient-local PrimeKG subgraph that surrounds the fine-tuning. The toggles let us experiment with which substrate gives the best ranking for Maureen.

Workflow

  1. Pick a section. Read its current row count + notes above.
  2. Inspect the data: hit the API with ?include=<key> and look at the JSON, or open the Patient Profile tab and toggle just that one on.
  3. Note any cleanup needed under “QC notes” (add bullets).
  4. When the data is good, check the section box at the top.
  5. When all sections are checked, the v1 substrate is QC’d and we can move to PRS computation + biomarker vector serialization (next iteration).

GH #108 status (2026-05-29) — fixed feature schema landed

The open QC items about which gene / biomarker subset feeds KGIA and stable PRS + biomarker vectors are answered by the committed, versioned cross-patient feature schema (backend/mods_kgia_schema_service.py, table pdr2_feature_schema, descriptor backend/pdr2_schemas/kgia_schema_v1.json):

  • expr_values is fed by mods_gene_expression (Caris WTS / RGCC gene expression), not the noisy biomarker_series section — so the vital-sign / imaging noise flagged for biomarker_series does not reach the model input. Gene axis = union of assay-observed genes ∩ canonical KG, ordered by symbol.
  • prs_values = supported PRS traits (default_disease_pgs_set()) ∩ KG, fixed across patients, ordered by CUI.
  • Every patient projects onto the SAME axis; a schema_hash + validate_against_schema guard train==infer.
  • New endpoint GET /api/mods/research/patient-profile/kgia-tensors returns the serialized vectors + hash + measured mask.

Still open (tracked, not blocking): biomarker categorization (#107) for the biomarker_series display section; cross-assay unit normalization (Olink NPX ↔ Caris percentile) once a non-Caris patient lands.

GH #114 — QC’ing the personalized ranking

Once a --use_ploss fine-tune exists (POST .../runs/{id}/submit_finetune), POST .../kgia/finetune/{run_id}/rank scores every candidate drug as a tail of (patient, MAPLE:sensitive_to_drug, ?) under that checkpoint. The ranked top-K lands on the run as a kgia_personalized_ranking validation row, read at GET .../kgia/finetune/{run_id}/ranking and rendered in the Research dashboard’s KGIA Ranking tab. Code: backend/mods_kgia_finetune_service.py.

[ ] QC the ranking, not just the profile

  • Which track was it? With no released PRS the fine-tune ran Track A (prs_values all zeros, so the disease weights got no gradient). Never describe a Track A ranking as PRS-personalized.
  • Anchor recovery. The payload’s anchors block gives the rank of drugs from her own record — her mods_treatment_episode drugs and her high_sensitivity RGCC agents. Deliberately not a clinical expectation list: an anchor has to trace to a row in her record, not to what is typical for her cancer type. A ranking that buries all of them is a finding about the ranking.
  • Read the held-out ranking. A candidate she already has a MAPLE:sensitive_to_drug edge to was in the foundation’s training data, so its rank is recall, not prediction (GH #214). Rows carry seen_in_training and a held_out_rank; the UI defaults to held-out-only.
  • Check counts.skipped — candidates the scorer could not resolve into the dataset vocab, usually drugs this composition excluded. A large fraction means the candidate set and the trained graph have drifted.
  • Sanity-check the spread. All candidates share one (head, relation) pair and one forward pass, so a near-constant score column means the model is not discriminating — not that every drug is promising.

Per MODS_MISSION_SPEC §1.4 a high score means the graph’s geometry is consistent with the drug being relevant; it is not evidence the drug works or is safe alongside her regimen.

Still open for #114: a one-click launch (stage the patient bundle to GCS and submit the fine-tune in one call) — today the pickle is built with scripts/build_pdr2_input_pickle.py and uploaded by hand.
