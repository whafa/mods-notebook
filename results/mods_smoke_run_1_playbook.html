Written: 2026-09-27 with Claude Opus 5.5, from a code, DB and artifact audit of work built mostly on Opus 5. Every number below was measured that day; re-verify any of them before you rely on it.

Outcome (2026-09-29). The run finished on 2026-09-29. All ten machinery checks (§6) were measured and pass; two of them, M6 and M9, were borderline, and Richard accepted both. Gate F released 590 scores over 109 diseases as smoke_v0. With her RGCC drugs held out of training, the base ranker shows no RGCC signal (graded-only ρ +0.03 and +0.05 per draw, intervals spanning zero), and the released criterion does not help. The rest of this page is the plan as written on 2026-09-27, with dated updates. Results: the run’s writeup and The smoke run lands.

The one-line version. We have never pushed Maureen’s real data through the whole machine. We have also never done it without her validation labels leaking into the training graph. This run does it once, deliberately, and checks every joint. Proving that personalization helps is not the goal. Proving that the machinery does what we think it does is.

0. What this run is, and what it is not

It is a machinery test on real inputs. The chain is:

  1. PRS released and normalized onto a disease axis, plus her expression values.
  2. A PDR2 patient pickle built from them.
  3. A criterion fine-tune on a foundation trained without her drug-response labels.
  4. Raw and personalized drug scores, stored side by side.
  5. Per-draw RGCC metrics.

It passes when every check in §6 passes.

It is not a test of whether personalization works. The released PDR2 criterion is degenerate, its sign is fixed, and it is blind to edge types (§1.4). A null or negative lift is the expected result. Report it; it is not a failure of this run. The science run is run #2 (§9).

It is pre-registered. Record the decisions in §3 as ticked boxes in #439 before any drug is scored. Look at no metric until the whole grid in §5.4 is computed.

Other drug-related leaks:

1.2 The graph has a symmetry leak

PrimeKG stores most edges in both directions under one predicate, and the export splits per directed triple. 539,594 of the 890,384 test triples (60.6%) have their exact reverse in train (Appendix A.3). Training does not remove the mirror (remove_one_hop defaults to False), so the foundation learns a lookup, and every PrimeKG foundation MRR (0.56–0.59) is inflated by it. This is the FB15k / WN18 inverse-leakage pattern. The split is also not reproducible. Set order depends on an unset PYTHONHASHSEED, and the audit found two same-seed runs sharing only ~21% of their test sets. On top of that, every downstream handler re-exports and re-splits, and re-adds the full patient overlay while doing it (#433).

PrimeKG’s MONDO:24331 carries only gene associations.

1.4 The criterion, as released

The released loss (losses.py, paper_code) is base + λ₁·tanh(ŵ·prs) + λ₂·tanh(v̂·expr), where ŵ and v̂ are L2-normalized. Neither term sees the batch, and the forward pass runs under no_grad, so:

  • The weights are closed-form. The optimum is ŵ = −PRS/‖PRS‖ and v̂ = −expr/‖expr‖. The fine-tune reads the input vector back out; it learns nothing from the graph.
  • The sign is fixed. Every disease term w_d·p_d ≤ 0 and grows with p_d². Drugs adjacent to her most extreme-risk diseases, high or low, get pushed down.
  • Expression never trained. It arrives as Caris TPM percentiles (4–100), unscaled, so tanh saturates from step 0. All 5 past fine-tunes ended with protein weights at their random-init scale. The “top protein weights” in earlier writeups are initialization.
  • Eval and training disagree about scale. Eval multiplies raw weights where training normalizes them, and it counts each adjacency 2–4 times depending on mirror and inverse structure.
  • The adjustment is edge-blind. An indication edge and a contraindication edge push the same way. That is Phase 12 (#420).

This run fixes the inputs and the eval/train mismatch (#435). It deliberately keeps the released loss, and measures the degeneracy (check M6 in §6). Phase 12 is the science fix.

1.5 Silent-failure modes still in the code

  • A failed checkpoint load continues on a random model (lib/pdr2/code/script/model.py, #434). A smoke run could “pass” on a random foundation. Fixed 2026-09-27 (#434): a failed load now raises.
  • Bare debug_log calls in the PDR handlers raise NameError. One of them sits between the Vertex submit and saving the job id, so a retry can double-submit an A100 job (#398). Fixed 2026-09-27 (#398).
  • Rebuilding the schema without --version overwrites v1 in place. Fixed 2026-09-28 (#497): --version is required, and an existing version is refused without --overwrite.
  • Releasing is one-way today. store_score_result never supersedes a released row, so a later re-score leaves old released values being served (#296’s writer needs a demotion path). Fixed 2026-09-28 (#296): the v0 release writer can demote a release (release_gate_f.py --demote).
  • The worker reloader used to hard-kill in-flight tasks on any .py change under C:\Maple, a git pull included (#361). It now drains instead: on a change to a module the worker imported (tests are ignored) it finishes the current task, then restarts. A task still running after WORKER_RELOAD_DRAIN_TIMEOUT_SECONDS (default 6 h; 0 = no deadline) is still killed. It has been off by default since 2026-09-28 (WORKER_AUTO_RELOAD=0). Don’t turn it back on during a pass.

5. Runbook

Every job goes through the worker queue or the research API, never raw gcloud, so each run lands in mods_research_run and the Training Cockpit.

5.0 Pre-flight and guardrails (before any long pass)

  • Worker reload is off. docker exec maple-worker-1 printenv WORKER_AUTO_RELOAD prints 0, the compose default since 2026-09-28. Then merges and pulls can go on during E3, D1, D2 or a Vertex handler; nothing needs freezing. A worker keeps the code it started with, so load merged code the way .claude/rules/worker.md describes. If it prints 1, recreate the workers from a C:\Maple that has the new default before starting.
  • Unattended fixer: pausing is optional. With reload off, that pull no longer restarts them.
  • Queue is clear. Nothing live in task_queue except the known stale rows: a pdr_checkpoint_eval claimed since 2026-05-27 (#313), and two March thread_embed rows.

    Reasoning paths for the top 10 (added 2026-09-29, Richard). For each of the ten, record the graph paths that drove its raw score. This is the evidence a reviewer would have to accept before taking the drug seriously. It is also the direct test of whether the ranking does more than recall known CRC drugs.

    • Method.

      • Use BaseNBFNet.visualize() in our fork (lib/pdr2/code/ultra/base_nbfnet.py). It takes the gradient of the score with respect to every edge, then beam-searches the highest-weighted paths (NBFNet’s interpretation method; defaults num_beam=10, path_topk=10).
      • Nothing calls it today. EntityNBFNet only gets its query and each layer’s relation inside Ultra.forward, so a thin wrapper must set both from the relation model first, exactly as forward does.
      • Running it needs a container mode, e.g. MODE=explain_paths. That is one more change to batch into the Lane R rebuild (§10). Submit it through the worker queue (M10).

    • Explain the exact score.

      • Use the same checkpoint, the same fact graph and the same query as score_edges.
      • visualize() skips negative_sample_to_tail, so pass the triple already turned: (CRC anchor, inverse of biolink:treats, drug).
      • Positive control: the score computed inside visualize() must equal the drug’s raw_score to float tolerance. If it doesn’t, the paths explain some other number: stop and fix the query.

    • Record per drug the top 5 paths with their weights, each hop as name, CURIE and predicate. Classify each drug’s strongest path:

      • direct: the drug’s own edge to CRC (expected for a known indication);
      • mechanistic: drug → target → gene or pathway → CRC;
      • analogy: drug → shared target or class → another drug → CRC;
      • personal: through her own node, via her expression, variant or phenotype edges (legitimate, since D2 keeps them);
      • hub: through a generic, very high-degree node.

      Report the count in each class. If every drug’s support is direct or analogy, the ranking is recalling known CRC drugs. Mechanistic paths are what repurposing needs.

    • Limits.

      • The paths explain the raw score only. The personalization adjustment is added after message passing and has no path; the “diseases whose PRS moved it” note covers it.
      • The foundation is frozen, so the paths are the same at every λ. Compute them once.
      • Gradient paths show what drove the score, not whether the biology holds.
      • No path may use one of the six predicates D2 excludes. One that does means M4 missed a leak.

8. What we will be able to say afterwards, and what we won’t

If M1–M10 pass, we can say:

  • The machinery runs end to end on real inputs with no drug-response leakage, and every artifact is traceable.
  • Her PRS reached the model at the right positions.
  • The honest base-ranker Tier-1 and Tier-2 numbers per draw. These are the first clean RGCC numbers the project has had.
  • How much the released criterion moves the ranking, in which direction, and through which edge types.
  • For each of the top 10, which graph evidence drove its raw score, and how much of the list rests on recall (direct or analogy paths) rather than mechanistic evidence.

We will not be able to say:

  • That personalization helps. The criterion is degenerate and edge-blind; that question belongs to run #2.
  • Anything clinical. Single patient; RGCC is in vitro, fixed-concentration CTC data; five Tier-2 positives.
  • That a path’s biology is true. The paths show what drove a score, so they are hypotheses to review, not findings.
  • Anything about patient-node queries (Mechanism A). This run does not use them.
