Kaiser FHIR sync: code review and completeness audit

Issue: #624, phase 1 (review and measurement; no code is changed). Code reviewed: main at 16f9ae0, after PR #626. Measured: 2026-10-01, read-only against production, counts only. Companion: backend/scripts/ehr/kaiser_census.py counts what Kaiser holds at the next login, which this audit cannot see.

(Status, 2026-10-05: most findings here are fixed in code. On 2026-10-02 every entry point began to run the sync in one place, decryption began to fail closed, every search pages to its end with retries and reports a short result as partial, OperationOutcome entries are set aside, connection lookups filter by provider, and next links stay on the FHIR site (findings 8, 11, 13 and 14, and §2). The same day, note and report text began to come from the attachments, uncut (findings 1 and 2); the post-May backfill ran (finding 3); records began to update in place by FHIR id (finding 7, and the encounter status in finding 9); the 306 older encounter copies were removed (§5); and an unstated condition status became “not stated” (finding 5). Richard decided the eight questions at the end on 2026-10-02 (D-Q4-16). Every count here is as measured on 2026-10-01.)

Richard has long suspected that Maple is missing documents. He is right, and the gap is larger than missing rows. Three things stand out:

  • Maple holds the record’s index, not its text. All 870 Kaiser clinical notes in Maple are empty shells: the note body was never fetched. Report narratives are stored only up to 500 characters, because Maple’s own importer keeps no more, and 35 of the 38 imaging and pathology reports in Maple stop exactly there.
  • Most of the record collapses on import. Kaiser returned 507 prescriptions and 391 conditions on 2026-10-01. Maple keeps one row per drug name (141) and one per condition name (42). Each row is frozen at its first import, and every condition stored from Kaiser reads “resolved”.
  • Nothing is ever updated. A record stored once is skipped on every later sync. Parser fixes from May never reached the rows stored before them. A status change at Kaiser never lands either. The patient knowledge graph turns those frozen statuses into the current_medication edges the PDR2 foundations train on.

The fetch layer is mostly sound after #626. The import layer is not: its identity keys are names and calendar days, not Kaiser’s ids, and that one design choice causes most of what follows.

2. Fetch

Paging. _fetch_all_pages follows next links but stops after max_pages=50 (5,000 entries at _count=100) with only a debug line (connector:453, 467). Observation and DiagnosticReport sort -date, so a capped search drops the oldest. No search reached the cap on 2026-10-01: labs used 27 pages (2,687 entries), vital signs 13, notes 10, reports 9. next links are followed to whatever host the server names, carrying the bearer token.

Bundle totals. Kaiser’s Bundle.total counts the page, not the search: the first page of a 1,213-entry search reports total=100. Nothing can use it as a completeness check. Whether _summary=count is supported and correct is unknown; the census records it beside the paged count.

Filters, sort, include. Every search is patient=<id>&_count=100; Observation adds a category, and Observation and DiagnosticReport sort -date. DiagnosticReport adds _include=DiagnosticReport:result, which made Kaiser take 266 s (#620; now under a 420 s read timeout). Kaiser does not expand the include for some reports. The direct-fetch fallback then got 403 on all 16 such results on 10-01, logged per observation and counted nowhere.

Delta. There is none for FHIR: every sync re-fetches the whole record. last_delta_timestamp is Cerbo-only, and even there the delta response is discarded. A full re-fetch is the right default for completeness. It only works if import is idempotent and applies updates, and today it does neither for most types (findings 4–7).

Timeouts and retries. Connect, write and pool use 30 s; the DiagnosticReport read uses 420 s. Nothing is retried: a 429, a 5xx or a dropped connection on any page raises. The pages already fetched for that type are discarded, so one bad page loses the whole type for that sync.

Non-resource entries. Every page carries exactly one extra entry (101 entries for 100 matches; 927 note entries over 10 pages for 917 notes), almost certainly an OperationOutcome. The fetchers parse it as the searched type. The Observation, Condition, MedicationRequest, Allergy, Immunization and Procedure parsers drop it because it has no name. The DocumentReference and Encounter parsers default it into a “Clinical Document” and an “Office Visit”. What Kaiser’s OperationOutcome says is never read.

How failures surface. Since #626 a failed search makes the sync partial, with failed_resources and fetch_errors, and a sync that fetched nothing is degraded. Still silent: the page cap, failed direct fetches, an HTTP 200 that is not a Bundle (zero entries), and import exceptions other than IntegrityError at commit, which mark the sync error while the counters already claim inserts.

Entry points. All three built-in paths fail on this machine (finding 8):

Lab and vital identity, in detail. The check is (series_id, ts), where ts is the date at midnight. Within one sync it runs as a query that, under autoflush off, cannot see values added earlier in the same sync. So same-day repeats were kept, and an observation that arrived twice (through the report _include and through its category search) was stored twice. Across syncs the same check sees the stored row and skips any new same-day result, or merges its metadata into the other row’s context. The stored data shows both:

  • 171 (series, day) groups hold 819 Kaiser-matched rows; in 159 of those groups every row was created on the same day;
  • 43 Kaiser observation ids are stored more than once in one series on one day;
  • 15 more ids sit in two different series, because the series cache keys on the case-folded name over every source with no tie-break (ingestion:467). Seven test names have two or more series.

The right identity is the Observation id. With it, repeats are distinct, a duplicate arrival is one row, and a corrected value can update in place.

Dates. _parse_fhir_date keeps the calendar date in the timestamp’s own offset (connector:1630–1631). Kaiser sends UTC, so a result after about 17:00 Pacific lands on the next day. A partial date (“2024-05”) becomes the first of the month with no precision marker.

Commit and rollback. import_fhir_data commits once, at the end (ingestion:1230–1236). That makes a sync atomic, which is good. But one bad row discards the whole sync’s import. Only IntegrityError is caught there, and the *_created counters are not reset.

Parsed, then dropped: presentedForm (all reports); the report’s status and category; DocumentReference attachment URLs, docStatus, relatesTo and encounter context; Observation status, code (the test code), comparator and component; Condition category and recordedDate; MedicationRequest intent, category, reasonCode and RxNorm coding; Encounter class, reasonCode and period.end. The procedure body_site is parsed into metadata but never into its column.

Notes by type label: Encounter Summary 310, Progress Notes 181, Telephone Encounter 126, Diagnostic imaging study 67, Staff Note 44, Patient Instructions 43, plus 25 smaller types (90 notes). A further 9 are the page-level junk entries (finding 14).

For comparison, all 121 manually uploaded documents and all 237 from the integrative practice carry the original file, and all but one carry extracted text (up to 1.28 M characters). Every full-text radiology report Maple has came that way, never from the sync.

.claude/rules/ehr-integrations.md says “FHIR is not a full-text source”. The code says otherwise: the sync never asks for the text. It cuts what it does get to 500 characters, and it throws away presentedForm unread. Whether Kaiser serves note bodies through Binary with this grant is the census’s attachment probe. The rule should be revised once that answer is in.

Import-day pairs: 303 ids were stored on 05-08 and again on 08-16; 1 on 05-08 and 10-01; 1 on 08-16 and 10-01. In every pair the later version is a superset of the earlier one: it adds the department or carries the final status and participants.

Recommendation. Keep the latest version of each id and delete the 306 older rows, after a backup, as #622’s cleanup did. Then change the sync to update in place, keyed on (patient, source, fhir_id) with a unique index. Store updated_at and the source’s meta.lastUpdated, and never overwrite with an older payload. The decision is Richard’s (below). The same rule should cover every FHIR type, not only encounters (finding 7).

6. Cross-source: kaiser_html against the FHIR rows

The March 2026 HTML import (307 encounters, 61 conditions, 15 medications, 8 immunizations, 4 procedures, 12 devices, 5 care-team members, 118 lab series) predates the FHIR sync and carries no Kaiser ids.

  • Encounters. 302 of 307 HTML encounters share a date with a FHIR encounter, 277 the type as well. Within the HTML date range (2016-12 to 2026-04), 300 of 303 FHIR encounters have an HTML row that day. Any view that does not filter by source counts these visits twice.
  • Conditions. 36 condition names appear under both sources. The HTML rows hold the encounter diagnoses (48) and the active problem list (10, 3 of them naming a cancer). 36 of the 42 FHIR rows carry one of those names, relabelled as resolved problems (finding 5).
  • Immunizations. Kaiser returned 12 immunizations on 10-01, and Maple holds 4 FHIR rows. The unique index (patient, vaccine, date) refused the other 8. The likely cause is the 8 HTML rows: the two sources name vaccines the same way (3 HTML names also appear on FHIR rows), and no HTML date matches a stored FHIR row. That is an inference; the census lists the 8 by date range. If it holds, no vaccination is lost, but those 8 carry no Kaiser id.
  • Medications. No name matches exactly; the two sources format names differently.
  • Labs. One series per name across sources, by design. 643 of 676 values in HTML-created series were later matched to a Kaiser observation id (finding 6).
  • Documents. One HTML document (social history); no overlap.

The HTML rows still hold data FHIR does not deliver today: devices, care team, surgical procedures, visit diagnoses and planned visits. They should be kept. Phase 2 needs a precedence rule: FHIR wins where both exist, and views read one source per type.

Phase 2: proposed order

  1. Census, at the next login, before any sync. Run kaiser_census.py first. It sends GETs only; my estimate is 10–15 minutes, and its output times every search. Then run the #621 backfill sync. Then, if the hour allows, run the census again with --types DocumentReference,DiagnosticReport to confirm the backfill. The first census sizes everything below: missing ids per type, how many results collapse, status drift, whether Binary and presentedForm are readable and how large, and what the procedure and care-plan searches return.
  2. Quick fixes, low risk, independent of each other: the key or runner (finding 8, #512); fail-closed decryption; the Terminal status; delta counts; resourceType filtering; no silent cap, plus retries; provider filters on connection lookups.
  3. Identity and updates (the core). Upsert on FHIR id for every type, unique indexes (a migration, numbered against all branches), and change tracking. Then the cleanups: the 306 encounter versions, re-importing collapsed medications and conditions as per-id rows, and de-duplicating lab values.
  4. Content. Binary note bodies and report forms, full observation text, embedding and categorisation of the new text.
  5. Fidelity: codes, statuses, categories, times, comparators, components and units, plus the condition category mapping.
  6. New types, chosen from the census counts: ServiceRequest and MedicationDispense first.
  7. Downstream. The patient KG reads the corrected medication and condition status; the freshness monitor (#512) watches series cadence.

The census

backend/scripts/ehr/kaiser_census.py runs inside the backend container, within the hour after a Kaiser login:

docker exec -i BACKEND python - < backend/scripts/ehr/kaiser_census.py
docker exec -i BACKEND python - --json < backend/scripts/ehr/kaiser_census.py > census.json
# once on main: docker exec BACKEND python -m scripts.ehr.kaiser_census --json

For each search it pages to the end, with no silent cap, and records:

  • pages, matches, distinct ids and non-resource entries;
  • Kaiser’s per-page total, and the _summary=count answer;
  • the date range;
  • OperationOutcome codes.

Per resource type it compares Kaiser’s ids with the ids Maple stores. It reports Kaiser-only ids (with their date range), Maple-only ids, and records Kaiser changed after Maple stored them.

It also counts what the sync’s parsers lose. For observations: status, comparators, text over 500 characters, the sync’s own (name, day) collisions, time of day, the day shift and stored values that differ. For conditions and medications: collapse on name and status drift. It counts attachment and form types. It fetches up to three attachments and reports their size and type, never their content.

It writes nothing. The database is read in one verified READ ONLY transaction, closed before any request. Every request is a GET to the stored FHIR host or another host of the same site (*.kp.org), and debug_log is silenced. Output is counts, codes, content types and date ranges only.

How the numbers here were measured

Read-only probes ran on 2026-10-01 against production, each with docker exec -i BACKEND python - < probe.py inside one SET TRANSACTION READ ONLY transaction (asserted with SHOW transaction_read_only), then rolled back. They printed counts, key names, FHIR codes and type labels only. Kaiser-side counts come from the debug_logs lines of the two 2026-10-01 syncs (page sizes, entries per search, parsed records), reduced to their numbers. Patient-scoped queries use Maureen’s patient id, which is also the earliest-created patient. No sync, census or write was run, and Kaiser was not called.
