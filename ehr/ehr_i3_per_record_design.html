Kaiser medications and conditions at one row per record

Issue: #624, Lane I, PR I-3. Decision: D-Q4-16 (#631) item 3, with items 2, 5 and 7. Builds on: I-2 (#674: migration 111 and mods_ehr_upsert). Code read: main at 855b437. Design only: no code, migration or database access went into this document. Where a number would change a recommendation, the read-only query is in Appendix A for the steward to run.

(Status, 2026-10-05: built and merged (PR #814) after Richard took every default in §7 (D-Q4-18). Where the build differs from this text, the implementation notes at the end say so. Counts in §1 are as of 2026-10-02.)

Maple keeps 141 Kaiser medication rows for 509 orders, and 42 condition rows for 392 conditions, because both tables are unique on a name. I-2 gave each stored row the Kaiser id of the record it was first imported from, and holds back every update to them. I-3 stores every record as its own row and turns updates on. “Current medication” and “active condition” then stop being a column that readers trust, and become a derived answer with written rules.

  • What it changes for her record. All 509 orders and 392 conditions are in Maple, and each stays in step with Kaiser: a stopped drug reads stopped, and an encounter diagnosis is no longer filed as a problem-list entry. “What is she on now” gets one answer with its reasons, which the Options Ledger’s safety check and the week-1 safety lane need.
  • What it changes for the model. Smoke run #1’s export excludes the medication edges (playbook D2), and Run #2 Arm A reuses that export, so none of the medication change reaches training. Condition edges are not excluded. biolink:has_phenotypic_feature edges built from mods_condition go into any export that includes maple_patient. Arm A is untouched. A later export, such as Arm B’s, would see I-3’s changes if the patient KG is re-materialized first (§5.4, J24).

0. Summary

  • Identity is already in place. Migration 111’s unique index on the Kaiser id is the identity. I-3 makes the two name indexes partial, covering only rows that have no Kaiser id. Kaiser records then never collapse on a name; the March HTML rows still dedupe exactly as today (§2.1).
  • The 137 + 42 stored rows with an id are already per-record rows, only stale. They stay, and each is updated in place from its own record, with every old value in mods_ehr_record_change. The first sync inserts the 370 orders and 350 conditions it collapses today. This replaces the hand-off outline’s “mark the old rows superseded” (§2.3).
  • Fidelity: I-3 also keeps intent, category, sig, dose, route, frequency and prescriber for orders, and category, verification status and recorded date for conditions (§2.2).
  • Derived views: one Python module classifies each record into a state, with an explicit rules table (§4). Consumers combine states by their own error costs. A safety screen over-includes; the KG under-asserts.
  • 24 judgment calls are flagged, each with a proposed default (§7). Most are vocabulary mappings, which CLAUDE.md reserves for Richard.
  • Proof: a read-only compare script builds the old and new KG edges from one database snapshot and explains every difference by a rule row (§5.5). A positive control has to pass: each drug of her maintenance regimen must read current or on hold.
  • Staging: backup, then merge, then compare on the same data, then a sync at a login, then compare again. The KG is re-materialized last, on a schedule that respects the Run #2 exports (§6).
  • Migration 113, free on every branch as of 2026-10-02. Re-check it at implementation time (§2.5). (Built as 116: see the implementation notes at the end.)

2. The schema change

2.1 Identity, and what happens to the name indexes

Identity is the Kaiser id, already enforced by migration 111. uq_mods_medication_source_record and uq_mods_condition_source_record are unique on (patient, source, resource type, id) where the id is set. I-3 adds no identity. It changes the two indexes that collapse records today:

Index todayColumnsAfter I-3
idx_mods_medication_dedupUNIQUE (patient_id, name)replaced by uq_mods_medication_name_without_id: the same columns, WHERE source_record_id IS NULL
idx_mods_condition_dedupUNIQUE (patient_id, name, category)replaced by uq_mods_condition_name_without_id: the same columns, WHERE source_record_id IS NULL

Why partial, not dropped. Rows without an id still need a key:

  • the March HTML rows (15 and 61): frozen, but a re-run must not duplicate them;
  • a reconnected Cerbo: its cerbo_id is not read as an identity yet, so its rows fall back to the name index, as today;
  • the 4 ambiguous rows, until J23 is applied.

For these rows the partial index is exactly today’s rule: the same columns, still across sources. A record with a Kaiser id never touches it. So medications_collapsed and conditions_collapsed drop to 0 for Kaiser records by construction, and any nonzero value is a defect to stop on.

It cannot fail on prod’s data. The partial index covers a subset of the rows the full index already keeps unique, which is migration 112’s argument. The migration:

  • builds the new index before it drops the old one;
  • copies 112’s transaction-scoped advisory lock and catalog check. Cloud Run and the local backend both run the chain at boot, and two chains creating one index name would fail a boot.

ModsMedication and ModsCondition declare the new indexes, and a test compares the declared shape with the migrated one, as tests/test_migration_112.py does.

2.3 How the existing rows map to per-record rows

The 137 medication and 42 condition rows that carry a Kaiser id are already per-record rows. Each was inserted from one record, the first to carry its name, and I-2’s backfill gave it that record’s id. What is wrong with them is that they are stale, not that they stand for a name. So I-3 keeps them and updates each one from its own record at the first sync. Every replaced value goes to mods_ehr_record_change.

This differs from the I-2 hand-off outline, which had the old rows marked superseded. Superseding:

  • would need a marker column on both tables and a filter in every reader;
  • would collide with the identity index: a superseded row keeps its id, so the fresh row for the same record would be refused;
  • would keep nothing that update in place loses. The history table holds every old value, and the pre-sync backup (§6) holds every old row.

4. The derived views

4.1 Shape

Per record, then per consumer. The view classifies each record into a state, and each consumer combines the states the way its error costs say:

  • A safety screen against her regimen must over-include. Missing a drug she takes is the dangerous error.
  • The knowledge graph must under-assert. An edge saying she takes a drug is a fact the explorer shows, and that a future export could train on.

A single “current” boolean cannot serve both, so the view never collapses to one.

One implementation, in Python. I recommend a module, for example backend/mods_ehr_derived.py, with a pure classifier per record type and thin readers over them, rather than a SQL VIEW. The rules are judgment calls that will change, and a SQL view would make every change a migration. The KG builder, the Terminal and the Ledger are all Python, so a SQL view would also be a second implementation that could disagree with the first. D-Q4-16 says “derived view”, meaning derived, not necessarily a SQL VIEW. Each rules-table row below becomes one test case.

Stamped. Every result carries:

  • rules_version (starting at ehr-derived/1) and as_of. The KG writes both into edge metadata, so a materialization built under older rules is visible by comparing the stored stamp with the code’s.
  • last_sync_at: the last Kaiser sync that fetched the type without a failure. “Current” means current as of that sync, and a sync needs Richard’s login: there is no refresh token. A consumer shows it beside the list.

Scope. Kaiser FHIR records (epic_fhir). The March HTML rows enter only where a rule row says so. Cerbo needs its own rows once it is reconnected (#512). Its prescriptions and supplements are exactly what a safety screen needs, and nothing here covers them yet.

Readers.

  • classify_medication_order(row, as_of) and classify_condition(row), both pure;
  • classify_medication_orders(rows, as_of): every order’s state, with M20 decided per drug (added 2026-10-08, §4.2). Every medication reader and the KG builder go through it;
  • medications(db, patient, as_of) → each order with its state and reason;
  • medications_to_screen(...), the safety list;
  • active_conditions(...), the active view.

They are served at GET /api/mods/clinic/medications/current and GET /api/mods/clinic/conditions/active, mounted in mods_clinic_api.py, which touches no registry hotspot. The Terminal serves them as ehr ls medications/current and ehr ls conditions/active.

Dates. as_of is a date, defaulting to today in Pacific time. Kaiser datetimes are stored as UTC calendar days (audit §3), so a window can be one day off at its edge. No rule below is that sensitive.

4.4 What settles the open calls

The 2026-10-02 census already counted most of what these calls depend on, per record type and with no record contents:

  • MedicationRequest: status, intent, with_rxnorm_coding, with_medication_reference, distinct_maple_names;
  • Condition: category / clinicalStatus, verificationStatus, with_icd10_coding.

5. What the patient KG emits after I-3

5.1 Medication edges

The builder classifies every Kaiser order and resolves each order’s drug as it does today: the name’s first word, then the full name, through DRUG_ALIASES. Then it decides per resolved entity (M13):

  • current_medication if any order is current;
  • otherwise past_medication if any order, or any March HTML row, is evidence she took it;
  • otherwise nothing.

Treatment-episode drugs still win (M18). Compared with today, on the same rows:

  • an order that is cancelled, a draft, entered in error, of unknown status, or not an order stops producing past_medication;
  • an active order outside its window moves from current_medication to past_medication;
  • a March HTML row reading active moves from current to past, unless a Kaiser order for the same drug is current;
  • a drug with one current and one ended order gets one current edge, never both.

5.2 Condition edges

One biolink:has_phenotypic_feature edge per resolved disease entity, from every record that is not void, refuted or unconfirmed, of any category and any status. That keeps today’s “has had” meaning, the one the foundations trained on. Compared with today, on the same rows:

  • refuted, entered-in-error and unconfirmed records stop producing edges;
  • each edge’s metadata is aggregated, not copied from whichever row came first.

The disease resolver matches names exactly, so most Kaiser condition names resolve to nothing today. docs/pdr_personalization_writeup.md counts 6 phenotype edges on her node. Expect the edge set to move little; the proof below measures it.

5.3 Edge metadata

Today the first row added wins. Both edge tables insert with ON CONFLICT DO NOTHING (mods_patient_kg_service 995 and 1018), and the builders read rows with no ORDER BY. With 509 orders for about 140 drug names, an edge’s status or start_date would then depend on row order: the tie-break the house rules forbid.

The rule instead:

  • Scalar keys: each key the edge carries today holds the value when every contributing record agrees. Otherwise it is NULL, and the distinct values are listed under <key>_values. The keys are name, status or clinical_status, category, rxnorm_code, route, dose_text, frequency, icd_code, snomed_code and abatement_date.
  • Dates: start_date and onset_date hold the earliest date.
  • Added: record_count, source_record_ids (sorted), state_counts, rules_version and as_of.

A shuffled input must give identical edges and metadata; a test checks it.

5.5 Proof: one snapshot, two builders

backend/scripts/ehr/compare_patient_kg_edges.py, new in the I-3 PR:

  • Read-only. One transaction, set READ ONLY and asserted with SHOW transaction_read_only, as the census does. Only the diagnosis, treatment-episode and medication builders run. They only read; the variant builder can upsert entities, so it is left out.
  • Two builders, one snapshot. It runs the pre-I-3 builders and the I-3 builders on the same rows, in memory, with no flush. The pre-I-3 builders are kept verbatim as *_v1 functions until the proof is filed on #624, then deleted.
  • Counts only. Per predicate and side (legacy, canonical) it prints edges before and after, kept, added and removed. It prints how many records each rule row decided, and a digest of the sorted (predicate, object) set per predicate. It prints no names, ids or values.
  • Every difference explained. Each added or removed edge must trace to a rule row. The script exits nonzero on any edge none explains.

It runs three times:

  1. After the merge, before the next sync. The same data, so every difference is a rule’s doing. The condition digest says whether training-relevant edges moved (J24).
  2. After the first post-I-3 sync. Old and new builders on the new rows: the rules’ effect on the full record.
  3. The new builder across the sync. Run 2’s new side against run 1’s: what the 720 new records and the in-place updates did.

The positive control from §4.4 runs before any of this is read as a result.

  • Interpretations, each open to change:
    • §5.3’s scalar rule counts an unstated value as a value: a key holds its value only when every record states the same one, unstated included.
    • end_date (“valid until”) is on today’s medication edge but not in §5.3’s key list; it is treated as a scalar. The edge also carries clinical_status_raw, per J19.
    • A “resolved entity” is a connected component: records that resolve to a common target on either side decide together, so no target can receive both medication predicates.
    • C15: a condition whose disease is the cancer profile’s adds no edge there; its aggregate rides on the profile’s edge under also_from.
    • M6 needs every dosage instruction to state a start after as_of; M17 calls an order without a start date not recent.
    • Medication and condition rows from a source other than Kaiser FHIR and the March HTML import (Cerbo, once reconnected) are not classified and contribute nothing; none exist.
    • The delta’s split uses start_date for orders and recorded_date for conditions, against the previous sync’s UTC day; an undated row is counted apart, never guessed.
    • The entity browser refuses edits to medication and condition rows with a Kaiser id only. Since I-2, encounter, immunization, allergy and procedure rows are overwritten by a sync too.

Implementation notes: M20 (2026-10-08)

The positive control failed at the first sync after I-3. Kaiser records each cetuximab infusion as its own MedicationRequest and marks it completed after the dose, so M8 read her current infusion as ended. Richard chose D-Q4-27 A (#873): a drug Kaiser records as repeated per-dose orders is current while its latest dose is within twice its own usual interval. It applies only to 3 or more completed orders at a regular spacing, so a one-off order never qualifies. Built as M20, RULES_VERSION ehr-derived/2. The decision fixes the 3 and the 2×. The rest is a reading of “at a regular spacing”, flagged for Richard on the PR:

  • A run, not the whole history. The latest dose must end a run of at least three, each dose at most 42 days after the one before. A longer gap is a break between courses, and the doses before it are not the drug’s spacing now.
    • Reading the whole history instead would let one order, months after an old series, read current for weeks.
    • The cost of the run: after a break, a resumed drug reads not current until its third dose. In those weeks the safety list still lists its orders as recent (M17).
  • 42 days. In her record the gaps between consecutive completed doses of one drug are either at most five weeks (a delayed cycle within a course) or more than eight (a break between courses). Six weeks sits between the two. It also caps the window at twelve weeks after the latest dose.
  • The lower median. With an even number of gaps, the usual interval is the lower middle one: an interval that occurred, and the shorter window.
  • Doses. A dose is a completed Kaiser order of the drug (not a plan), counted once per start day. The start (authoredOn) is the only date a dose has, because Kaiser refuses our app’s MedicationAdministration requests.
  • What stops it. An order of the drug dated on or after its latest dose, or undated, that is stopped, on hold, cancelled, a draft or of unstated status. An active order is decided by M4–M6; one entered in error is void. M20 changes no order but the completed one(s) on the latest dose day.
