PrimeKG → Biolink Predicate Mapping — Final Report

Authors: whafa, Claude (Maple project) Date: 2026-05-09; last updated 2026-05-11 with actual post-rerun audit numbers Companion writeup: kg_composition_pipeline_writeup.md §4.1 + §4.2 Code: backend/kg_normalize/predicate_mapper.py Trigger: during the post-migration audit (writeup §4.1) we observed 250 PrimeKG edges had collapsed to fewer canonical relations than legacy. That was acceptable per se (predicate canonicalization is supposed to dedup synonymous edges), but a closer look showed the mapping table had three real bugs and several unnecessarily coarse choices. This document is the post-fix audit of every PrimeKG → Biolink mapping with a defensibility tag for each.

Status update 2026-05-11. The refined mapping was deployed, both PrimeKG and GP-KG canonical schemas were wiped and re-migrated, and the actual post-rerun numbers are now embedded throughout this report (sections marked “Actual …” below). Predictions and actuals are both retained so the reader can see how well the prediction held up.

Summary

PrimeKG ships 30 distinct relation types. After mapping they collapse to 23 distinct Biolink predicates (up from 16 in the original mapping). All 7 remaining collapses fall into one of three defensible categories:

  • AMBIGUITY-VIA-DOMAIN — multiple raw predicates map to the same Biolink predicate, but the subject/object entity domains (drug vs gene vs phenotype, etc.) carry the disambiguating signal. A model that consumes entity types — which both PDR1 (CompGCN) and PDR2 (ULTRA) do — can recover the distinction. Loss is theoretical, not practical.
  • DELIBERATE-LOSS — two raw predicates encode the same biological fact (or one is a strict subset of the other). Collapsing is correct, not lossy.
  • EXACT — Biolink has a directly equivalent predicate; the mapping is canonical.

Every PrimeKG raw predicate is preserved verbatim in the mods_kg_relation.source_predicate column. The predicate column carries the canonical Biolink form. Downstream consumers can use either or both.

Mapper coverage vs data presence

These are different things and worth distinguishing:

  • The mapper has 23 distinct Biolink predicates defined for PrimeKG.
  • The actual data only contains 20 distinct Biolink predicates because three of the mappings (biolink:has_carrier, biolink:has_enzyme, biolink:has_transporter) target raw PrimeKG predicates (carrier, enzyme, transporter) that PrimeKG documents in its schema spec but never actually emits in the version of the data we ingested.
  • The 3 missing predicates correspond to PK-style drug-protein relationships (carrier proteins, metabolizing enzymes, transporters) that probably require a downstream DrugBank tier PrimeKG didn’t include.

This is benign — the mapper is future-proofed: if PrimeKG ships an update that includes those rows, our pipeline handles them automatically with the right Biolink predicate, no code change needed. The 20→23 gap is “schema-anticipated mappings vs data-realized mappings,” not data loss.

On general principle

The lesson here is generalizable: predicate canonicalization is a lossy transformation by definition (you’re projecting a high-dimensional relation type space onto a lower-dimensional one). The right framing isn’t “is information lost?” — yes, always — but “is the loss recoverable, defensible, and intentional?” Three knobs to tune:

  1. Use Biolink’s specific predicates when they exist. biolink:has_off_label_use is a thing; biolink:subclass_of is a thing. The first pass of this mapper used biolink:treats and biolink:related_to as defaults, which silently lost recoverable distinction.
  2. Preserve the source value verbatim in a separate column so the loss is recoverable for any consumer that needs it.
  3. Tag the loss tier in the mapping comments — EXACT vs AMBIGUITY-VIA-DOMAIN vs DELIBERATE-LOSS. Whoever inherits this code (including future-you) gets to evaluate each choice on its own terms rather than re-deriving them from scratch.

This applies to any other source we add (CIViC, OncoKB, PharmGKB, RTX-KG2). The connector tests should include an “all source predicates have a defensible mapping with a tag” check as part of D-phase acceptance.

Why Biolink seems “too small” — the qualifier-vs-predicate model

(Adding this section to address a recurring question: if Biolink has hundreds of predicates, why do we keep collapsing source-native predicates into smaller numbers of canonical Biolink predicates?)

Biolink IS big at the predicate level — it ships hundreds of slot definitions. But the appearance of “Biolink being too small to cover what we have” comes from three real architectural choices Biolink makes that differ from how individual KGs structure their data:

1. Biolink models qualifiers separately from predicates

When a source like CIViC says “PREDICTS_SENSITIVITY_TO drug X for cancer type Y at evidence level 3A”, the source compresses everything into one relation type per (predicate, qualifier-combination). Biolink instead models this as ONE predicate (biolink:predicts_sensitivity_to) PLUS separate qualified_predicate, subject_aspect_qualifier, evidence_level slots that carry the extra structure.

Our current schema (mods_kg_relation) has columns for subject_id, object_id, predicate, source_predicate, source_id, weight, evidence, metadata. There’s no qualifier column. So when a source represents an evidence-level distinction as a separate relation type (e.g., PrimeKG’s indication vs off-label use), and Biolink would naturally model both as biolink:treats with different qualifier values, our schema makes us choose:

  • Map both to biolink:treats → loss (this was the original PrimeKG bug we just fixed)
  • Use different Biolink predicates if available (biolink:treats vs biolink:has_off_label_use) → preserves the distinction at the predicate level (current refined approach)
  • Add qualifier columns to our schema → cleanest, but bigger refactor; deferred

So Biolink IS big enough to express everything, but our schema doesn’t yet model the qualifier dimension where Biolink puts ~30% of the information.

2. Biolink uses entity-type-domain to disambiguate, on purpose

Take drug_drug (drug-drug interaction) and protein_protein (protein-protein interaction) — semantically very different! Biolink maps both to biolink:interacts_with (the same predicate) because the subject and object entity types already convey the distinction. A (drug, biolink:interacts_with, drug) row means DDI; a (protein, biolink:interacts_with, protein) row means PPI.

This is a design choice: Biolink avoids predicate redundancy when entity types convey the information. A downstream model (CompGCN, ULTRA, etc.) typically embeds entity types alongside predicates, so the distinction is recoverable.

You can see this in our refined PrimeKG mapping: protein_protein and drug_drug both → biolink:interacts_with (3,314,778 rows total in PrimeKG canonical, of which 2,672,628 are drug-drug and 642,150 are protein-protein — recoverable via entity-type filter).

3. Some source predicates are inherently multi-semantic

PrimeKG’s gene_go_phenotype covers gene→GO-term relationships, but GO has three subgraphs (Biological Process, Molecular Function, Cellular Component) with semantically distinct relationships:

  • Gene → BP term should be biolink:participates_in
  • Gene → MF term should be biolink:enables
  • Gene → CC term should be biolink:located_in

PrimeKG flattens all three into one relation type without exposing the GO subgraph metadata. We have no honest way to pick the right Biolink predicate per row, so we map to biolink:related_to (the parent predicate). This is one of two DELIBERATE-LOSS entries in our PrimeKG mapping table. 204,862 rows in GP-KG and similar in PrimeKG sit at this related_to placeholder until/unless we re-process those edges with the GO subgraph membership lookup.

So: Biolink is comprehensive at the predicate-AND-qualifier level. Our schema currently captures only the predicate dimension. Apparent collapses are typically Biolink working as designed (entity-type disambiguation) or our schema lagging (missing qualifier columns). In every case, the raw source_predicate column preserves the source’s distinction verbatim — no information is irretrievably lost.
