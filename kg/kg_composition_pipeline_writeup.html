Summary

Before this session, the Maple MODS pipeline had two biomedical knowledge graphs loaded — GP-KG and PrimeKG — via ad-hoc per-source code with no registry, no canonical CURIE layer, no composition concept, and no programmatic way to swap or combine sources for a training run. Adding a third source (CIViC, OncoKB, PharmGKB, or RTX-KG2) would have meant rewriting the export script. Verifying license posture, deduplicating across sources, or understanding “which entities does this composition cover?” required ad-hoc SQL.

We built a six-phase refactor (A–E with one planning-only Phase F) that introduces:

  • A source registry (mods_kg_source) — the canonical record of every biomedical KG we know about, with status, license, citation, and live row counts.
  • A domain taxonomy (mods_kg_domain) — Tier 1/2/3 classification of entity domains so compositions can filter by gene, drug, disease, etc. without per-source string-matching.
  • A canonical entity layer (mods_kg_entity / mods_kg_entity_source / mods_kg_relation) — one row per real-world thing keyed by Biolink CURIE, with provenance moved to a join table. Cross-source deduplication becomes a single GROUP BY instead of fuzzy name-matching.
  • A composition primitive (mods_kg_composition / mods_kg_composition_member) — named, versioned graph mixes that training runs reference by ID. Six baseline compositions seeded.
  • An Entity Resolver with pluggable upstream (NCATS Node Normalizer, ClinGen Allele Registry, predicate mapper) for canonical CURIE resolution at ingest time.
  • Four new source connectors (RTX-KG2 KGX, CIViC, OncoKB, PharmGKB) implementing a BaseKGConnector ABC.
  • A REST API + dashboard tab + MCP tools for inspecting the canonical schema and composition validator output without dropping into psql.
  • A legacy → canonical migration that backfilled all 129,375 PrimeKG nodes and 8,099,878 / 8,100,128 (99.997%) of PrimeKG edges into the new schema with zero synthetic CURIEs and zero unmapped predicates. The 0.003% gap is fully accounted for by intentional canonicalization dedup.

The session also surfaced (and fixed) two operational bugs worth recording: a per-row insert pattern that turned a should-be-10-minute migration into a 6.8-hour one (fixed: ~750× bulk-insert speedup), and a cursor advancement bug that caused all 8M+ PrimeKG edges to be permanently orphaned on the first migration attempt (fixed: auto-reset edges cursor when nodes are added, plus a --rewalk-edges escape hatch).

1. Purpose

A ranked list of drugs is a claim about biology, and anyone asked to act on it is entitled to ask what it was computed from. Which sources went in. What each one actually contributed. How two records naming the same drug were decided to be the same drug. What is still missing, and whether the gap matters. If the answer to any of those is “there is a markdown table someone maintained by hand, and a set of ingest scripts that each made their own decisions,” then the honest response to why should anyone believe this is that they should not — and that is true no matter how good the model on top turns out to be.

The stake is specific rather than abstract. The output of this pipeline is meant to reach one patient’s oncologist, and the first question a clinician will ask about a surprising candidate is where it came from. A pipeline that cannot answer that has not earned the conversation. So this work is not infrastructure for its own sake: it is the difference between a number and a number somebody can check.

The objectives below all reduce to making the data layer auditable end to end — which, put less grandly, means being able to answer the four questions in the first paragraph from the database rather than from memory.

The concrete objectives going into the session:

  1. Registry and provenance — every KG we’ve ingested or are considering should be a database row with license, citation, and status, not a markdown table maintained by hand.
  2. Cross-source identity — when two KGs both contain Olaparib, the system should know it’s the same drug. Not via string-match heuristics; via canonical Biolink CURIE.
  3. Composition — training runs should be able to declare “I want PrimeKG plus CIViC variants, filtered to Tier 1 domains” and have that be a configuration value, not a script edit.
  4. Defensible domain coverage — for any composition, we should be able to say which Tier 1 domains have how many entities, what the license posture is, and where the gaps are.
  5. Pluggable connectors — adding a new source should be a one-day task: write a connector that subclasses a base ABC, register it in the source registry, run an ingest job. No rewrites elsewhere.
  6. Variant-graph readiness — Phase 8.5 wants variants (BRAF V600E, DPYD*2A, UGT1A1*28) as graph-native nodes. The schema should support this without a follow-on refactor; the connector framework should make CIViC/OncoKB/PharmGKB ingest trivial.

The scope did not include rewriting the existing KG explorer or MCP tools that read from the legacy mods_kg_node / mods_kg_edge tables — that consumer cutover (Phase C4 in the plan) is real work whose value depends on the new schema actually getting populated and exercised, so it was deferred until after the headline goal lands.

2. Materials and Methods

2.1 Pre-session state (what existed)

  • Two KGs loaded into mods_kg_node / mods_kg_edge: GP-KG (61,146 nodes, 1,246,726 edges) and PrimeKG (129,375 nodes, 8,100,128 edges). Both keyed by (kg_source, external_id) — the same canonical entity (e.g., Olaparib) appeared as two rows linked only by name match.
  • One markdown registry: docs/KG_CATALOG.md, hand-maintained.
  • One export script: backend/scripts/export_primekg_for_pdr.py — hard-coded WHERE kg_source = 'prime_kg'.
  • One MCP-aware translator query connector: backend/connectors/translator_connector.py — query-time enrichment only, never bulk ingest.
  • Three planning docs that referenced this work: pdr_phase8.5_variant_kg_planning.md, temporal_patient_modeling_planning.md, and the parent we-need-more-rigor-fuzzy-nygaard.md (drafted at session start).

Three things to point at:

  1. Identity moved into its own table. mods_kg_entity is one row per real-world thing keyed by canonical CURIE; mods_kg_entity_source is the many-to-one provenance join. The same drug now collapses to one entity, with N source rows under it — corroboration is a GROUP BY entity_id.
  2. Sources and domains are first-class. Adding a new KG is now an INSERT into mods_kg_source + a connector, not a new magic string scattered through queries. Domain taxonomy with tiers makes composition filters declarative.
  3. Compositions decouple “what’s in the graph” from “what we train on.” mods_research_run.composition_id points at a versioned recipe; the same canonical store backs every experiment.

Schema rationale. The new design separates two concerns the legacy schema conflated:

  • Identity — what real-world thing is this? Canonical CURIE in mods_kg_entity.curie. UNIQUE index. One row per drug/gene/disease/variant in the universe.
  • Provenance — which sources have it, under what native ID, with what source-specific metadata? mods_kg_entity_source rows, one per (entity, source, external_id) triple.

This means cross-source corroboration becomes a single SQL aggregate (the headline win):

Without the refactor, “find drugs that PrimeKG and CIViC both link to BRAF V600E” was a JOIN on lowercased names with hand-written aliases. With it, it’s a join on shared entity_id.

2.3 Entity Resolver (backend/kg_normalize/entity_resolver.py)

The resolver mediates between connector output (EntityRecord dataclasses with optional curie_hint and biolink_category_hint) and canonical storage. Resolution flow per record:

  1. Cache lookup — has this CURIE hint been resolved before? mods_kg_curie_cache is a memoizing layer keyed on hint.
  2. Upstream resolver — pluggable. In production this is ChainedResolver([ClinGenAlleleRegistryClient(), NodeNormalizerClient(), PredicateMapper()]). The default for tests / cold-start is SyntheticOnlyResolver() (no-op).
  3. Hint as canonical — if no upstream confirmed but the connector supplied a CURIE hint (e.g., PrimeKG’s metadata gives us MONDO:0005148), use it directly. This is the key to dedup working without a live Node Normalizer.
  4. Synthetic fallback — <source_id>:<external_id>, tagged is_synthetic_curie=true so the validator can surface the rate.

The resolver supports both per-row (resolve_entity) and bulk (bulk_resolve_entities) entry points. The bulk path issues exactly four SQL statements per batch regardless of size; we’ll come back to why that matters in §3.4.

2.4 Connector framework (backend/connectors/base.py)

BaseKGConnector is an ABC with three required methods (manifest, is_downloaded, download, stream_relations) plus optional hints. The manifest mirrors the columns of mods_kg_source so registry rows can be auto-upserted on first ingest. EntityRecord and RelationRecord are dataclasses connectors emit; the resolver consumes them.

2.5 Composition layer (backend/mods_kg_composition_service.py)

A composition is a named, versioned recipe: “use these sources, apply these per-source domain and predicate filters.” Materializing it runs a CTE that walks mods_kg_entity_source and mods_kg_relation filtered by composition members. The service exposes:

  • CRUD (create_composition, get_composition, lock, unlock)
  • materialize(composition_id) → entity_ids + relation_ids ready for export
  • validate(composition_id) → non-blocking report covering domain coverage, license posture, dedup stats, missing-CURIE percentage, orphan count, coverage gaps
  • coverage_report(composition_id) → counts by (source, domain) for UX surfaces

Per the parent plan’s user direction, validate() is informational only — it never blocks ingest or composition. License posture (e.g., “OncoKB is in this composition; OncoKB is non-permissive”) is surfaced for humans to decide on, not enforced.

2.6 Export pipeline

backend/scripts/export_composition_for_training.py replaces the legacy export_primekg_for_pdr.py. Takes --composition-id and --format pdr|kgx. Produces train/valid/test splits using the same greedy + 60/20/20 algorithm the legacy script used, so existing PDR training notebooks accept the output unchanged. The legacy export script is preserved as a thin shim for backward compatibility.

2.7 UX surface (Phase E)

Three additions:

  • REST API (backend/mods_kg_api.py) at /api/mods/kg/*: list/get sources + compositions, validation report, coverage report, lock/unlock, global stats.
  • Lab dashboard tab (frontend/src/components/ModsKGCompositionTab.jsx): three-panel view — overview tiles (entity/relation/source/synthetic-CURIE counts), sources table with status badges, expandable composition cards with validate/lock actions and rendered validator reports.
  • MCP tools in backend/mcp_servers/mods_server.py: mods_kg_list_sources, mods_kg_list_compositions, mods_kg_get_composition, mods_kg_validate_composition, mods_kg_canonical_stats. All callable from the terminal as /<tool> slash commands.

2.8 Legacy backfill (backend/scripts/migrate_legacy_kg_to_canonical.py)

A two-phase walk per source:

  • Phase 1 (nodes). Read mods_kg_node ordered by id, build a CURIE hint from metadata.original_source + metadata.original_id (PrimeKG carries these natively) or by parsing the external_id (DB\d+ → DRUGBANK:, C\d{7} → UMLS:, etc.). Pass through the resolver, populate mods_kg_entity and mods_kg_entity_source.
  • Phase 2 (edges). Build a legacy_node_id → canonical entity_id map by joining the populated mods_kg_entity_source to mods_kg_node. Read mods_kg_edge ordered by id, resolve each edge’s subject/object via the map, normalize the relation_type via the predicate mapper, bulk-insert into mods_kg_relation.

Both phases use a cursor in mods_kg_migration_state for resumability. Both are idempotent (ON CONFLICT DO NOTHING on the canonical tables).

A PowerShell wrapper backfill_kg.ps1 at the repo root handles Cloud SQL Proxy startup, loads DATABASE_URL from .env, and forwards arguments to the Python script — the user invokes the entire pipeline as one command.

3.4 The migration: what went wrong and how it got fixed

This is the part worth dwelling on — both bugs are common patterns and both have lessons that generalize past this work.

Bug 1: per-row INSERT vs cloud DB latency.

The first migration attempt was structured as a per-record loop:

Each resolve_entity call did roughly: cache lookup, INSERT entity ON CONFLICT DO NOTHING, SELECT entity id, INSERT entity_source ON CONFLICT DO UPDATE. With ~30 ms of round-trip latency per statement to the Cloud SQL proxy, that’s ~120 ms per record. For PrimeKG’s 129,375 nodes, total wall-clock was 6 hours, 49 minutes, 42 seconds (24,582.8 s as logged).

The fix was to batch: bulk_resolve_entities(records) issues exactly four SQL statements regardless of batch size — bulk cache lookup, multi-value INSERT entities, SELECT ids by curie, multi-value INSERT entity_sources. For a 1000-record batch that’s 3,000 round-trips → 4 round-trips ≈ 750× speedup at cloud latency. The estimate held: re-running PrimeKG’s nodes phase after the fix takes minutes rather than hours.

Worth stating plainly, because the intuition runs the other way: inserting a thousand rows is not a thousand times the work of inserting one. On the wire it is very nearly the same work. What costs is the round trip — the ~30 ms of waiting between “here is a statement” and “here is your answer” — and that price is paid per statement, not per row. A loop issuing four statements per record pays it four times per record. A batch issuing four statements per thousand records pays it four times, full stop.

The practical consequence is that profiling misleads in this class of workload. Nothing in the per-row path is slow; no single call is doing anything wasteful, and a CPU profile of the migration would have shown a program spending almost all of its time idle and told you nothing about what to fix. The unit that matters is not operations, or rows, or CPU seconds. It is statements crossing the network, and it is worth counting them explicitly before concluding a job is inherently long-running.

Bug 2: cursor advancement on skipped edges.

The edges phase walked all 8.1M PrimeKG edges in id order, advancing a cursor in mods_kg_migration_state every batch. Conceptually:

The problem: the first migration attempt had been run with --limit-nodes 1000 (a smoke test). That populated only 1000 canonical entities; the edges phase walked all 8.1M edges, found that ~99.7% of them referenced the other 128,375 yet-to-be-backfilled nodes, skipped them, and advanced the cursor to the maximum edge id. The follow-up “now do the rest” run correctly added the remaining 128,375 entities — but the edges phase saw cursor = max_id, fetched zero edges, and exited.

The legacy mods_kg_edge table still contained all 8.1M rows; the canonical mods_kg_relation table only had the 20,874 edges from the limited first run. 8M+ relations were silently orphaned.

This was caught by the user noticing the dashboard’s Canonical relations: 20,874 was implausibly low compared to PrimeKG’s stated 8.1M edges. We diagnosed by inspecting the cursor row — it was at the very last edge id, not at “the last successful insert” — and the architecture flaw became immediately visible.

The fix has two parts: (a) when the nodes phase processes > 0 rows in a run, automatically reset the edges cursor for that source so previously-skipped edges get re-walked; (b) a --rewalk-edges manual flag for cases like the user’s, where nodes are already complete but edges are stuck. Both rely on ON CONFLICT DO NOTHING for idempotency — re-walking already-inserted edges is a no-op.

The narrow bug is one line. The wider one is a conflation, and it is the part worth carrying: a cursor recording where the walk reached is not the same object as a cursor recording what the walk accomplished, and this loop used one variable for both. A seek position is a statement about the input; a bookmark is a statement about the output. They agree exactly as long as nothing is ever skipped — which is to say they agree right up until the first run that skips something, and that run was the smoke test.

What makes it dangerous rather than merely wrong is that both failures are quiet. The first run skips 99.7% of its input and reports success, because skipping was a legitimate outcome for every edge it saw. The second run fetches zero rows and also reports success, because reaching the end of a stream is not an error. Nothing throws, no count is obviously wrong in isolation, and the only surviving evidence is a total that happens to look implausible next to a number published elsewhere — which is exactly how it was found, and not a detection method anyone should rely on twice.

The general form: when a loop can decline to act on an item, “I have seen everything” and “I have done everything” stop being the same claim, and a resumable job needs to persist the second one.

4. Results

4.1 PrimeKG canonical backfill — full audit (BASELINE; first migration with coarse mapper)

Reader note: this section is the baseline audit from the first PrimeKG migration (2026-05-08). It reflects the coarse predicate mapping that was in place at the time, which produced a 250-edge canonicalization gap and 16 distinct Biolink predicates. The refined mapper + re-migration was triggered by analysis of these numbers; see §4.3 for the final audit on the refined data. Both audits are preserved so the reader can verify the gap, the cause, and the fix end-to-end.

The 63-entity gap. PrimeKG’s x_index is its internal guaranteed-unique identifier (the connector uses it as the canonical external_id). But several x_index values resolve to the same (original_source, original_id) pair when we extract the CURIE hint from the row’s metadata. In other words, PrimeKG’s own data contains two distinct x_index rows for the same real-world entity in 63 cases.

PrimeKG’s authors documented this as approximately 64 collisions; we measured 63. They’re not data loss — they’re correct deduplication of source-side duplicates. The user’s KG_CATALOG.md flagged this as a known issue when PrimeKG was first imported.

The 250-edge gap. This was the more interesting number. We confirmed via SQL audit that the gap is entirely caused by predicate canonicalization dedup, not by any data loss:

Result: 8,100,128 / 8,100,128 / 8,099,878.

The 250 missing edges are pairs where PrimeKG records the same (drug, disease) relation as both indication AND off-label use. Both raw predicates map to biolink:treats per the predicate mapper, and the unique constraint on (subject, object, predicate, source) collapses them to one canonical row. This is the correct semantic behavior — those are genuinely the same fact recorded twice in the source.

Other potential collapse vectors in the predicate mapper (e.g., bioprocess_protein + pathway_protein both → biolink:participates_in, or protein_protein + drug_drug both → biolink:interacts_with) would only collide if the same (subject, object) pair appeared with multiple raw predicates. PrimeKG mostly avoids this by domain-typing its edges (a protein-protein edge can’t share endpoints with a drug-drug edge), so those didn’t contribute to the dedup count.

Three real bugs were fixed and several over-coarse defaults refined; details in kg_predicate_mapping_report.md.

The headline contribution: 4,421 variant entities — the entity class neither PrimeKG nor GP-KG carries. The connector framework’s EntityRecord schema with curie_hint and biolink_category_hint handled the variant-as-graph-node case without any schema changes.

Two problems surfaced during the ingest that are worth recording — both quiet failure modes that the framework’s defensive design caught only after the data landed:

1. CIViC’s TSV download URL had changed. The connector hardcoded https://civicdb.org/downloads/nightly/EvidenceSummaries.tsv from when it was first written; CIViC has since reorganized to a nightly-AcceptedAndSubmittedClinicalEvidenceSummaries.tsv naming. The old URL now 200-OKs with the 1.7 KB SPA HTML, so the connector cheerfully reported a successful download with evidence_size_mb: 0.0. First fix: update the filenames to the current convention (verified via the CIViC GraphQL dataReleases query). Lesson: connectors should sanity-check downloaded payloads (content-type, minimum-size) before declaring success.

2. CIViC’s variant TSV uses placeholder strings (N/A, NONE FOUND, unregistered) in identifier columns. The connector was building CLINVAR:N/A as a CURIE hint and the EntityResolver dutifully treated it as a canonical identifier — collapsing 283 distinct biological variants onto one shared mods_kg_entity row. The validator surfaced this as an unusually high variant_sources count per CLINVAR:* curie. Second fix: a _clean_id() helper that filters known placeholder values to None before forming the CURIE; variants with no real ID then fall through to the synthetic fallback (as they should). Wipe + re-ingest yielded the correct 4,421 distinct variants.

The two bugs together pushed the first-pass node count from 5,724 to the correct 6,014 — a 5% identity-graph correction that would have silently degraded downstream cross-source matching once OncoKB and PharmGKB land.

Schema evolution in the upstream source. CIViC’s 2025 schema introduced a molecular_profile layer that abstracts over variant (1 MP = 1+ variants). The connector originally read variant_id from evidence rows; the new schema ships molecular_profile_id and pushes variant_id to the join via single_variant_molecular_profile_id in VariantSummaries. The patched connector now resolves MP → variant for single-variant profiles (the common case) and falls through to MP-as-opaque-entity for multi-variant profiles. Two-line change to _row_to_relations plus a new mp_to_variant index. Source-schema evolution is going to be a recurring theme as we add more connectors; the connector framework’s separation of “where does the data live” from “what shape is it” keeps this kind of upstream churn local to the connector file.

Performance. The end-to-end ingest took 14 minutes for 10,943 evidence rows at ~14 relations/sec — driven by the per-row EntityResolver.resolve_entity round-trip cost (3-4 SQL statements per record × 30ms cloud RTT). Fine for CIViC’s scale. RTX-KG2’s 6.5M entities × 140M relations would extrapolate to ~150 hours at this rate — the bulk path (bulk_resolve_entities, ~750x faster) becomes mandatory for Phase D0. Tracked as an explicit pre-D0 prerequisite.

mods_kg_source.status is now loaded for CIViC with node_count=6014, edge_count=11474, ingested_at=2026-05-12 23:13:35Z. The tier1_mvp_v1 composition now materializes with non-zero CIViC contribution.

4.6 The composition pipeline as a research lever

The composition primitive immediately enables a class of experiments that were friction before:

  • Cross-source corroboration scoring. Train on primekg_baseline_v1, then for each predicted candidate, count how many sources independently assert the same (subject, object, predicate) tuple. Higher = more confidence. This is now a GROUP BY query, not a custom script.
  • License-aware compositions. “What does my graph look like if I exclude OncoKB and any PharmGKB-derived edges?” One composition definition; immediate answer.
  • Domain ablation. Train on tier1_mvp_v1, then on tier1_mvp_v1 excluding variant domain, and measure the lift.
  • Patient-anchor scoping. Phase F (planning doc landed) extends the composition primitive with an anchor_set_id so a composition can mean “all of X intersected with N hops of Maureen’s anchor entities.” Critically, this is NOT a way to define the production training set (that would destroy the discovery loop) — it’s a post-hoc filter / fine-tune target / explainability surface. The planning doc covers six distinct use cases; F.5 (inference candidate filtering) is the single most product-relevant.

5. Discussion

5.1 What we’d do differently

Bulk-insert from day one. The per-row resolver was correct but operationally unusable at production-DB scale. Adding the bulk_resolve_entities method as a separate code path (vs retrofitting resolve_entity to bulk under the hood) felt right because it keeps the per-row API for streaming connectors that genuinely yield records one at a time. But the bulk path should have existed before the first migration attempt rather than being added as a fix after a 6-hour wait.

Cursor semantics need to be explicit. “Where I left off” and “what I successfully did” are different things and cursor design has to pick one and commit to it. Our fix (reset on nodes-added + manual --rewalk-edges flag) treats the cursor as a seek hint, not a finality marker, which works for our use case because every operation is idempotent. If we ever add a non-idempotent operation downstream, this cursor design will need a re-think.

Test coverage was good but missed the operational shape. We had 128 passing unit tests against synthetic data. They didn’t catch either bug because both manifest only at scale (the per-row latency penalty) or in a specific interaction sequence (cursor advancement after a partial run). Adding even one integration test that runs the backfill against a 10,000-row synthetic dataset and times it would have flagged the perf issue immediately.

5.2 Limitations

  • Phase C4 (consumer cutover) is deferred. The legacy KG explorer, MCP tools (mods_kg_search, mods_kg_find_path, etc.), and saved-subgraphs (mods_kg_subgraph / mods_kg_subgraph_item from migration 069) all still read the legacy mods_kg_node / mods_kg_edge tables. The new dashboard tab and REST API read the canonical schema. Both data layers coexist correctly; they just don’t share a UI yet. The cutover is real work, and it should be driven by which canonical-schema feature gets used first.

  • No new sources actually ingested yet. D0–D3 connectors are code-complete and unit-tested but haven’t been pointed at real data. RTX-KG2 in particular needs a multi-GB KGX bundle download; CIViC needs a few-MB nightly TSV pull; OncoKB needs an academic API token; PharmGKB needs a manual download from their downloads page. The dashboard will surface “loaded” vs “planned” status correctly once each lands.

  • The legacy backfill script is one-shot. It exists to migrate the existing GP-KG and PrimeKG data into the canonical schema. After GP-KG runs (the only remaining backfill), the script can be retired. New sources go through the connector framework directly — they never touch mods_kg_node / mods_kg_edge.

  • The predicate mapper is hand-curated. Six sources × ~20 raw predicates each = ~120 mapping entries currently. As we add more sources or PrimeKG/CIViC/OncoKB ship updates with new relation types, the mapper needs maintenance. The validator surfaces the unmapped-predicate rate per composition, so coverage gaps are at least visible — but a more principled approach (e.g., LLM-suggested Biolink mappings with human review) is a candidate future improvement.

  • The Entity Resolver’s hint-as-canonical fallback can produce CURIE drift. If the connector’s hint uses a different prefix casing than the canonical Biolink form (e.g., NCBIGene:673 vs NCBIGENE:673), and Node Normalizer isn’t wired in to canonicalize, two effectively-identical hints land as two distinct entities. We saw this once during testing and fixed it by removing the over-aggressive .upper() call in the hint construction. With Node Normalizer wired in (currently optional via --use-node-normalizer), this drift is invisible because every hint round-trips through a canonical-form authority. Worth wiring as default for a future ingest pass.

5.3 Retiring the legacy backfill

After GP-KG is migrated (the last remaining source in mods_kg_node / mods_kg_edge), the path forward is:

  1. Verify GP-KG migration with the same audit pattern — total node count, edge count, synthetic CURIE rate, unmapped predicate rate, expected-collapse delta.
  2. Lock the baseline compositions (gp_kg_baseline_v1 and primekg_baseline_v1) — mods_kg_composition_service.lock(id) flips is_locked = true so accidental edits can’t shift training sets out from under reproducibility.
  3. Stop using mods_kg_node / mods_kg_edge for new work. New sources go through the BaseKGConnector framework into the canonical schema directly.
  4. backend/scripts/migrate_legacy_kg_to_canonical.py can be retired — kept in git history but removed from the active codebase. The backfill_kg.ps1 wrapper retires with it.
  5. Phase C4 (consumer cutover) becomes the next blocker for legacy table removal. Until KG explorer / MCP tools / saved subgraphs are migrated to read canonical, migrations 079 (rename to *_legacy) and 080 (drop *_legacy) stay deferred.

5.4 What’s next

In order of expected value:

  1. D1 CIViC ingest. Public, permissive, the easiest of the variant connectors to bring online. Closes the variant-domain gap immediately for cancer variants. Estimated: half a day including audit.
  2. D2 OncoKB ingest. Requires the academic API token. Adds FDA-aligned actionability (Level 1/2/3A/3B/4/R1/R2) which directly maps to Maureen’s clinical decision context. Estimated: half a day.
  3. D3 PharmGKB ingest. Requires manual download. Closes the chemo-safety gap (DPYD, UGT1A1, TPMT, CYP2D6) — directly relevant to her CRC treatment plan. Estimated: half a day.
  4. Re-run training on tier1_mvp_v1. Once D1–D3 land, the headline composition is no longer empty. Compare downstream metrics (RGCC validation, AD case study Spearman ρ) against primekg_baseline_v1 to measure variant-extension lift.
  5. Phase F.1–F.4 (anchor scoping inspection layer). Even before full Phase F, getting “Maureen’s 2-hop neighborhood” visible in the dashboard delivers immediate value for inspection and explainability.
  6. Phase C4 (consumer cutover). Once the canonical schema is the primary data substrate by usage, the legacy explorer / MCP tools / saved subgraphs cutover becomes the gating step for retiring mods_kg_node / mods_kg_edge.
  7. D0 RTX-KG2 ingest. Lower priority than D1–D3 because RTX-KG2 overlaps PrimeKG significantly and the marginal value is mostly in the protein domain (which mods_kg_entity will keep separate from gene, unlike PrimeKG’s normalization). Worth doing for completeness and as a third corroboration source.
