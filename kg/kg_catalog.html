Query via the mods_kg_list_sources and mods_kg_list_compositions MCP tools. Always defer to the DB for exact counts and current status; the snapshots in this file are illustrative.

ULTRA Pretraining KGs (non-biomedical)

These three datasets aren’t biomedical and don’t enter the MODS pipeline directly. They’re the standard pretraining mix for ULTRA (Galkin et al., ICLR 2024) — the relation-invariant foundation model that PDR2 builds on. ULTRA’s whole pitch is that it doesn’t memorize entities or relations; it learns the structure of the relation graph. To learn that, it needs exposure to varied relation patterns — dense vs sparse, broad vs taxonomic, factual vs modern. These three together cover that space well enough that the trained model transfers zero-shot to 50+ unseen KGs (including biomedical ones like Hetionet and PrimeKG) without fine-tuning.

ULTRA paper: Galkin M, Yuan X, Mostafa H, Tang J, Zhu Z. “Towards Foundation Models for Knowledge Graph Reasoning.” ICLR 2024. arxiv:2310.04562. Mirror at docs/References/ULTRA/.

These KGs are not tracked in mods_kg_source; they live in the PDR2 vendor tree (lib/pdr2/) and are only used for pretraining the ULTRA backbone.

Planned experiment — 64d vs 128d ULTRA pretraining

Current ULTRA pretraining (lib/pdr2/) uses 64-dimensional hidden representations. Planned sweep: re-pretrain on the same three-KG mix (FB15k-237 + WN18RR + CoDEx-M) at 128d and compare:

  • (a) Standard link-prediction metrics (MRR, Hits@k) on the three pretraining datasets
  • (b) Zero-shot transfer to GP-KG and PrimeKG (the targets we actually care about)
  • (c) Downstream impact on per-patient PDR2 fine-tune AUPRC (Maureen + RGCC validation)

Hypothesis: larger capacity may help on harder transfer targets, but the pretraining set is small (combined ~565K triples) so over-parameterization is a real risk. Worth measuring rather than assuming. Track in a follow-up writeup under docs/pdr2_* when run.

Adding a New KG

To add a new knowledge graph to the pipeline:

  1. Connector: Create backend/connectors/<kg_name>_connector.py implementing:

    • is_downloaded() → bool
    • download(progress_callback) → Dict
    • stream_triples(batch_size) → Generator[List[Tuple], None, None]
    • get_stats() → Dict
    • data_summary() → Dict
    • count_triples() → int

  2. Register in DB: Insert a row in mods_kg_source (or use the bootstrap path that wires it during worker/task_handlers.handle_import_kg). Set initial status='planned', fill citation / source_url / license / version. Status auto-advances to running then loaded during ingest.

  3. Load: Trigger via mods_kg_import MCP tool or directly through ModsKGCanonicalService.import_from_connector(kg_source, connector).

  4. Validate: Run mods_kg_canonical_stats and mods_kg_list_sources to confirm live counts line up with what the connector said it would emit.

  5. Composition (optional): If the new KG should participate in a training run, add a member row in mods_kg_composition_member for the relevant composition(s), with any include_domains / include_relations filters.

  6. Document here: Add a section under “Loaded KGs” with paper / DOI / domain fit narrative and known issues. Don’t duplicate node/edge counts or license text — those live in the DB.

  7. Feature tables (optional): If the KG ships supplementary node features, extend mods_kg_disease_feature / mods_kg_drug_feature or create new tables via migration.

Critical: Preserve source entity types and relation types exactly. Never collapse finer-grained types into coarser ones during import. See “Data and Mapping Integrity Rules” in CLAUDE.md — this rule was paid for in real data loss.
